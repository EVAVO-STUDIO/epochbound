# Campaign Data Contract

Epochbound content is stored as versioned JSON so campaigns can be reviewed in Git, validated without opening scenes, generated by tools and installed independently of the engine code.

## Directory layout

```text
campaigns/
  campaign_id/
    campaign.json
    maps/
      first_map.json
      second_map.json
```

Packaged campaigns use `res://campaigns`. Installed player campaigns use the equivalent structure under `user://campaigns`.

## Identifier rules

Identifiers are lowercase and may contain:

- `a-z`
- `0-9`
- `_`
- `-`

Identifiers are references. Titles and display names are presentation. A map may be renamed for players without changing its identifier.

## Campaign manifest

A `campaign.json` file currently contains:

```json
{
  "schema_version": 1,
  "id": "example_campaign",
  "title": "EXAMPLE CAMPAIGN",
  "subtitle": "A NEW JOURNEY",
  "author": "Campaign Author",
  "description": "An original Epochbound campaign.",
  "start_map": "first_crossing",
  "start_era": "verdant",
  "map_files": ["maps/first_crossing.json"],
  "intro": ["First page.", "Second page."],
  "actors": {
    "player": {"name": "HERO", "max_health": 32},
    "companion": {"name": "COMPANION", "max_health": 24}
  },
  "ruleset": {
    "combat_model": "action",
    "companion_enabled": true,
    "era_shifting_enabled": true
  }
}
```

`map_files` only accepts safe relative JSON paths. Absolute paths, parent-directory traversal and protocol paths are rejected.

## Map record

A map file contains these top-level records:

- `schema_version`
- `id`
- `display_name`
- `canvas`
- `bounds`
- `spawns`
- `eras`
- `layers`
- `interactions`
- `connections`

### Canvas and bounds

`canvas` defines the authored world dimensions and grid size. `bounds` defines the legal actor movement rectangle inside that canvas. The runtime camera follows the player across maps larger than the 640 by 360 presentation viewport.

### Spawns

Every map currently provides stable `player` and `companion` spawn positions. Later connection records will select named arrival anchors rather than using only the default pair.

### Eras

Each era contains:

- a stable identifier;
- a player-facing display name;
- a validated HTML hexadecimal palette;
- era-specific landmark records.

The current primitive renderer supports `marker`, `sun`, `ruin`, `well`, `tree` and `dead_tree` landmark kinds. These are blockout contracts, not final art categories. Later records will reference tile sets, sprite scenes, animation sets and environment profiles while retaining the same stable landmark identity.

### Layers

Supported layer types are:

- `terrain`
- `objects`
- `collision`
- `navigation`
- `effects`

Each layer has a unique identifier, z-index, visibility state and lock state. The first editor slice previews records but does not yet expose full tile or polygon editing.

### Interactions

An interaction currently contains:

```json
{
  "id": "old_well",
  "kind": "well",
  "position": {"x": 124, "y": 207},
  "radius": 58,
  "available_eras": [],
  "dialogue": {
    "verdant": "Dialogue in one era.",
    "ashen": "Dialogue in another era.",
    "default": "Fallback dialogue."
  }
}
```

An empty `available_eras` array means the interaction is available in every era. Dialogue may be a single string or an era-keyed object.

### Connections

Connections are reserved for map exits and entrances. Validation already ensures each declared `target_map` resolves to a map in the same campaign. The next editor slice will add visual connection placement, named arrival anchors and reciprocal-link checks.

## Schema evolution

Every campaign and map declares `schema_version`. New engine versions should add explicit migration functions rather than silently interpreting old data differently.

Migration rules:

1. Never destroy the original file before a migrated copy validates.
2. Migrations move forward one version at a time.
3. Runtime loading rejects unsupported versions with a useful error.
4. Editor saves use the current schema only.
5. Stable identifiers and world-state keys survive migrations.

## Save-game separation

Campaign definitions describe authored content. Save games describe a player's state inside that content. Save records must reference campaign ID, campaign content version, map ID, era ID and stable world-state keys; they must not copy entire campaign definitions.

This separation allows campaigns to be updated while still giving the loader enough information to reject or migrate incompatible saves deliberately.
